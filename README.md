# Discography

Web application to manage the musical records of a discography firm. Technical test for
**CodiTramuntana**.

It is a Spring Boot REST API backed by SQLite, with a small static single page frontend
that exists only to exercise the API from a browser.

---

## Tech stack

| Layer | Choice |
|---|---|
| Language / runtime | Java 21 |
| Framework | Spring Boot 3.5.6 (Web, Data JPA, Validation) |
| Persistence | Hibernate 6.6 + **SQLite** (`org.xerial:sqlite-jdbc`, `hibernate-community-dialects`) |
| API documentation | springdoc-openapi 2.8.15 (Swagger UI) |
| Build | Maven, through the included wrapper (3.9.11) |
| Tests | JUnit 5, Mockito, AssertJ, MockMvc |
| Frontend | Vanilla ES modules, native `<template>` elements, CSS3 — no Node, no build step |

## Database

- Engine: **SQLite 3**, file `discography.db` created in the working directory on startup
  (together with the `-wal` and `-shm` companion files). All three are git-ignored.
- The schema is generated by Hibernate (`ddl-auto: update`).
- **To reset the data**: stop the application, delete `discography.db*` and start again.
  The seed data is loaded again automatically.
- The location can be overridden with the `DB_PATH` environment variable.

## Domain model

```
Artist 1 ────< N Lp 1 ────< N Song N >──── N Author
```

- An `Artist` has many `Lp`s; an `Lp` belongs to exactly one `Artist`.
- An `Lp` has many `Song`s. Songs are part of the LP aggregate: deleting the LP deletes them.
- A `Song` has many `Author`s and an `Author` writes many `Song`s (join table `song_authors`).
- `Author` is a shared catalogue: authors are reused by name and never deleted automatically.

## API reference

Full, browsable documentation is at `/swagger-ui.html`. Summary:

### Artists

| Method | Path | Description | Status codes |
|---|---|---|---|
| GET | `/api/artists?name=` | List artists, optionally filtered by partial name | 200 |
| GET | `/api/artists/{id}` | Artist detail, **including its total number of LPs** | 200, 404 |
| GET | `/api/artists/{id}/lps` | **LPs belonging to the artist** | 200, 404 |
| POST | `/api/artists` | Create | 201, 400, 409 |
| PUT | `/api/artists/{id}` | Update | 200, 400, 404, 409 |
| DELETE | `/api/artists/{id}` | Delete | 204, 404, **409 if it still owns LPs** |

### LPs

| Method | Path | Description | Status codes |
|---|---|---|---|
| GET | `/api/lps?artistName=` | List LPs, **filtered by partial artist name** | 200 |
| GET | `/api/lps/{id}` | LP detail with its songs and their authors | 200, 404 |
| POST | `/api/lps` | Create | 201, 400, 404, 409 |
| PUT | `/api/lps/{id}` | Update | 200, 400, 404, 409 |
| DELETE | `/api/lps/{id}` | Delete the LP and its songs | 204, 404 |
| POST | `/api/lps/{lpId}/songs` | Add a song with its authors | 201, 400, 404, 409 |
| PUT | `/api/lps/{lpId}/songs/{songId}` | Rename a song and replace its authors | 200, 400, 404, 409 |
| DELETE | `/api/lps/{lpId}/songs/{songId}` | Remove a song | 204, 404 |

### Authors and reports

| Method | Path | Description | Status codes |
|---|---|---|---|
| GET | `/api/authors` | Author catalogue, used to reuse existing authors | 200 |
| GET | `/api/report/discography` | **Home page report**: LP, artist, song count, authors | 200 |

Errors always share the same shape:

```json
{
  "timestamp": "2026-09-09T20:15:30.123",
  "status": 409,
  "error": "Conflict",
  "message": "Artist 'Metallica' cannot be deleted because it still has 2 LP(s)"
}
```

## Branching strategy

The repository follows Vincent Driessen's **git-flow** model:

| Branch | Purpose |
|---|---|
| `main` | Production state. Only ever receives merges from `release/*`, always tagged. |
| `develop` | Integration branch. Holds the deliverable state of the next version. |
| `feature/*` | One capability per branch, started from `develop` and integrated with `git merge --no-ff`. |
| `release/1.0.0` | Delivery preparation: final documentation and versioning. Merged into `main` and back into `develop`. |

Every integration uses `--no-ff` on purpose: the merge commit records both parents and the
branch name, so each feature keeps its own bubble in the history graph even though the
branch itself is deleted once integrated, exactly as the model prescribes.

The nine features were integrated in dependency order — `project-setup` → `domain-model` →
`rest-api-foundation` → `artist-and-lp-crud` → `discography-report` → `sample-data` →
`api-documentation` → `automated-test-suite` → `web-frontend` — so **every point along the
integration line of `develop` compiles and passes the test suite**.

To read the history:

```bash
git log --graph --oneline --first-parent develop   # the integration line
git log --graph --oneline --all                    # the full graph, with every feature bubble
```

One honest caveat: the tests live in a single `feature/automated-test-suite` branch because
that reflects how the work actually happened — the suite was written once the domain model
and the REST layer had settled. On a team practising continuous delivery, each feature would
carry its own tests instead.

## Design decisions

These are the choices worth explaining, and why they were made.

**REST API plus a static frontend, instead of server side rendering.** The assignment
allows any stack and the accompanying email asked for a very basic frontend and a solid
backend, so the backend is a self contained REST API and the UI is a thin client over it.
It also keeps the API testable on its own and documented through Swagger.

**The report runs exactly two queries, never one per LP.** The home page report needs, per
LP, the artist, the number of songs and the distinct authors of those songs. It is resolved
with two aggregated JPQL queries assembled in the service, so the number of statements is
constant no matter how large the catalogue grows. Two alternatives were evaluated:

- A native query with `GROUP_CONCAT`: SQLite cannot combine `DISTINCT` with a custom
  separator, and it does not guarantee the ordering of the concatenated values, which would
  make the output non deterministic and the SQL engine specific.
- A single fetch join of the whole graph: it produces a cartesian product of songs by
  authors just to compute a count.

`LpRepositoryReportTest` asserts the statement count, so a future regression into an N+1
would fail the build.

**Deleting an artist that still owns LPs returns 409.** `lps.artist_id` is not nullable, so
the options were cascading or refusing. Silently destroying a whole discography is a poor
default for an API, so the invariant is made explicit and the caller decides what to do.
Deleting an LP does cascade to its songs, because a song has no meaning outside its LP.

**Authors are never deleted automatically.** They are a shared, reusable catalogue: removing
the last song of an author must not make the author disappear, or reusing it later would be
impossible. Authors are resolved by name in a single query, and only the missing ones are
created.

**`GenerationType.IDENTITY` for every entity.** SQLite has no sequences, so `AUTO` would
fall back to a table generator, adding a parasite table and extra statements that compete
for SQLite's single writer lock.

**SQLite pragmas travel in the JDBC URL.** SQLite disables foreign key enforcement by
default and the pragma is per connection, so it must apply to every connection the pool
opens. Hikari's `connection-init-sql` only runs a single statement, so the URL is the clean
place for `foreign_keys`, `journal_mode=WAL` and `busy_timeout`.

**Entities compare by persisted identifier only.** Lombok's generated `equals`/`hashCode`
would walk the whole bidirectional graph, causing infinite recursion and forcing lazy
collections to load. Comparing only by id has a subtlety of its own: brand new entities all
share a `null` id, so they must be equal only to themselves, otherwise a `Set` of unsaved
songs would collapse into a single element.

**A Java seeder instead of `data.sql`.** The assignment asks for "Rails seeds or the
equivalent seeds method", and seeds in Rails are code. It also matters here that the SQLite
file survives restarts, so seeding must be idempotent, and that identifiers are generated
by the database, which a raw SQL script would have to hardcode to populate the join table.
The seeder reuses the same author resolution logic the API uses.

**Tests run against SQLite, not H2.** The whole risk surface of this project is the SQLite
integration: DDL generation, identity columns, `TEXT` columns and `lower()`/`LIKE`
behaviour. A green suite on H2 would prove none of it.

**Hash based routing in the frontend.** With the History API, reloading a deep link such as
`/lps/3` would ask the server for that path and get a 404 unless a forwarding controller
were added. With hashes the browser always requests `/`, so deep links and refreshes work
with no server side configuration.

**No pagination.** A discography catalogue is bounded, and the report is by definition a
full table. Adding it later means changing the repository signatures to accept a `Pageable`
and wrapping the response; the decision is deliberate, not an omission.

## Known limitations

- **SQLite allows a single writer at a time.** WAL mode and a busy timeout make this a non
  issue at this scale, but the engine would not be the right choice for a concurrent
  production workload.
- **`ddl-auto: update` cannot migrate a SQLite schema.** SQLite's `ALTER TABLE` cannot
  change column types or add constraints, so after changing an entity the database file has
  to be deleted and recreated. A real deployment would use explicit migrations.
- **Case insensitive uniqueness is enforced in the service layer.** SQLite unique indexes
  are case sensitive, so the index acts as a backstop while the service performs the actual
  check.
- No authentication: the assignment does not ask for it and it would add noise to the review.
